## 1. Общие сведения

### 1.1. Назначение системы
Платформа повышает вовлечённость студентов во внеучебную жизнь колледжа. На ней:
- студенты видят календарь мероприятий, записываются на них и подтверждают посещение;
- студенты выполняют задания и проходят опросы и голосования;
- за активность студенты получают внутреннюю валюту — **степы**;
- степы тратятся в магазине мерча, а за активность можно участвовать в розыгрышах призов;
- администрация колледжа получает отчёты о посещаемости и активности студентов.

### 1.2. Цели
1. Один источник информации обо всех мероприятиях колледжа.
2. Прозрачная и измеримая система поощрения активности.
3. Автоматический учёт посещаемости и участия, без бумажных списков.
4. Отчётность для администрации с выгрузкой в Excel.

### 1.3. Масштаб
- Студентов: около 1500. Запас по производительности — до 3000.
- Администраторов: 2–10.
- Групп: около 60–80. Курсов: 1–4.
- Пиковая нагрузка: одновременная отметка посещения 300 студентами на крупном мероприятии.

### 1.4. Формат
Адаптивный веб-сайт. Основной сценарий использования — со смартфона, у администраторов — с компьютера. Сайт можно установить на телефон как приложение (PWA) и получать пуш-уведомления. Нативные мобильные приложения в объём работ не входят.

### 1.5. Термины
| Термин | Значение |
|---|---|
| МЭШ | Московская электронная школа (для колледжей — МЭШ СПО, school.mos.ru) |
| СУДИР / mos.ru ID | Система единого входа Правительства Москвы, через которую работает вход в МЭШ |
| Степы | Внутренняя валюта платформы. Название настраивается |
| Заработанные степы | Сумма всех начислений за период. Покупки её не уменьшают. По ней строятся рейтинги |
| Баланс | Степы, доступные для трат: начислено минус потрачено |
| Чек-ин | Подтверждение посещения мероприятия |

## 3. Авторизация и учётные записи

### 3.1. Вход через МЭШ (целевой вариант)
Студенты МЭШ СПО входят через единую систему авторизации mos.ru (СУДИР). Для подключения платформы как внешней системы нужно:
1. Подать заявку в ДИТ Москвы на подключение информационной системы к СУДИР по протоколу OAuth 2.0 / OpenID Connect. Порядок подачи и состав документов **уточняются** (см. раздел 13).
2. Получить `client_id`, `client_secret` и адреса точек авторизации, токена и данных пользователя.
3. Согласовать набор получаемых данных (scope): идентификатор пользователя, ФИО, e-mail. Если доступно — роль и образовательная организация (группа).

**Сценарий входа:**
1. Студент нажимает «Войти через МЭШ».
2. Платформа перенаправляет его на страницу входа mos.ru. Используется Authorization Code Flow, параметры `state` и PKCE.
3. После входа платформа обменивает код на токен и запрашивает данные пользователя.
4. Платформа ищет студента по идентификатору МЭШ. Если не находит — сопоставляет с импортированным списком (п. 3.3).
5. Создаётся сессия платформы. Токены МЭШ после входа не хранятся.

**Требования:**
- Параметры интеграции (адреса, ключи, соответствие полей) задаются в настройках сервера, а не в коде.
- Если студента нет в импортированном списке, вход запрещается. Студент видит сообщение «Вас нет в списках, обратитесь к администратору», а попытка попадает в журнал.
- Если пользователь по данным МЭШ не является обучающимся этой организации (когда такие данные доступны), вход запрещается.

### 3.2. Резервный вход (до подключения МЭШ и как запасной вариант)
Подключение к СУДИР может занять продолжительное время, поэтому в первой версии нужен резервный способ входа:
- при импорте из Excel система создаёт каждому студенту логин и одноразовый пароль;
- администратор выгружает для каждой группы листы с доступами и раздаёт их через кураторов;
- при первом входе студент обязательно меняет пароль;
- пароль сбрасывает администратор (новый одноразовый пароль);
- после подключения МЭШ резервный вход можно отключить для студентов в настройках. Администраторам он остаётся.

Администраторы входят по логину и паролю. Вход через МЭШ для них опционален. Для суперадминистратора рекомендуется двухфакторная аутентификация (TOTP) — во второй версии.

### 3.3. Импорт студентов и сопоставление с МЭШ
**Импорт из Excel (.xlsx)** по шаблону:

| Колонка | Обязательна | Пример |
|---|:-:|---|
| Фамилия | ✔ | Иванова |
| Имя | ✔ | Мария |
| Отчество | | Сергеевна |
| Группа | ✔ | СИП-21 |
| Курс | ✔ | 2 |
| Специальность | | 09.02.07 |
| E-mail / логин mos.ru | | ivanova@mail.ru |
| Дата рождения | | 12.03.2008 |

Требования к импорту:
- шаблон файла можно скачать;
- перед загрузкой показывается предпросмотр: сколько записей будет создано, обновлено, сколько ошибок, и построчный список ошибок;
- импорт повторяемый: существующие студенты обновляются (перевод в другую группу), а не дублируются;
- студентов, которых нет в новом файле, можно пометить как «выбывших». Тогда вход блокируется, а история сохраняется;
- группы создаются автоматически по названию из файла.

**Сопоставление при первом входе через МЭШ** — по порядку:
1. По e-mail или логину mos.ru, если он указан в импорте.
2. По ФИО и дате рождения.
3. По ФИО, если совпадение единственное.
4. Если сопоставить не удалось или найдено несколько совпадений, запись попадает в очередь «Несопоставленные входы». Администратор вручную привязывает её к студенту или отклоняет.

После привязки идентификатор МЭШ сохраняется, и дальнейшие входы проходят без сопоставления.

### 3.4. Профиль студента
- ФИО, группа, курс (только для чтения).
- Аватар — опционально, загружает студент, с модерацией.
- Баланс и заработанные степы.
- История операций со степами.
- Мои мероприятия, задания, заказы, розыгрыши.
- Полученные достижения.
- Настройки уведомлений.

## 4. Внутренняя валюта «Степы»

### 4.1. Название
Рабочее название — **степы** (от англ. step — шаг): каждое действие студента — шаг вперёд. Варианты с той же идеей: «шаги», «ступени», «импульсы». Название в единственном и множественном числе (для склонения: 1 степ, 2 степа, 5 степов) и иконку суперадминистратор задаёт в настройках.

### 4.2. Принципы
- Степы — целые положительные числа.
- **Баланс не может быть отрицательным.** Штрафных списаний нет.
- Любое изменение баланса — запись в **журнале операций**. Записи журнала не редактируются и не удаляются. Ошибки исправляются только новой операцией (сторно).
- Баланс всегда равен сумме операций журнала. Хранимое значение баланса для быстрого чтения обновляется в той же транзакции, что и запись журнала.
- Каждое начисление привязано к источнику. Повторное начисление за тот же источник невозможно (идемпотентность).
- Степы не сгорают. Периоды используются только для рейтингов.

### 4.3. Источники начисления (автоматически)
| Источник | Когда начисляется | Сумма |
|---|---|---|
| Мероприятие | При подтверждении посещения | Задаётся в мероприятии |
| Задание с ручной проверкой | При принятии администратором | Задаётся в задании. Администратор может назначить меньше, но не больше максимума |
| Задание с автопроверкой | При правильном ответе | Задаётся в задании |
| Опрос | При отправке ответов | Задаётся в опросе (можно 0) |
| Голосование | При голосовании | Задаётся (по умолчанию 0) |
| Достижение | При получении | Задаётся в достижении (можно 0) |

### 4.4. Ручное начисление
- Администратор начисляет степы одному студенту, нескольким выбранным или целой группе.
- Обязательные поля — сумма и причина (например, «Призёр олимпиады», «Волонтёрство на Дне открытых дверей»).
- Есть лимит одного ручного начисления (по умолчанию 500) и лимит на администратора в сутки. Оба задаёт суперадминистратор.
- Начисления сверх лимита требуют подтверждения суперадминистратора.
- Есть отдельная операция «Сторно» — отмена ошибочного начисления. Она невозможна, если степы уже потрачены и баланс уйдёт в минус. В этом случае администратор видит предупреждение.

### 4.5. Типы операций журнала
`event_attendance`, `task_reward`, `survey_reward`, `vote_reward`, `achievement_reward`, `manual_credit`, `reversal` (сторно), `purchase`, `purchase_refund`.

## 5. Модуль «Календарь мероприятий»

### 5.1. Карточка мероприятия
| Поле | Обязательно | Комментарий |
|---|:-:|---|
| Название | ✔ | |
| Описание | ✔ | Форматированный текст, ссылки |
| Обложка | | Изображение |
| Категория | ✔ | Справочник: спорт, творчество, учёба, волонтёрство, профориентация и т.п. |
| Дата и время начала и окончания | ✔ | |
| Место | ✔ | Аудитория, адрес или «онлайн» со ссылкой |
| Аудитория | ✔ | Все студенты, или выбранные курсы, группы, специальности |
| Запись | ✔ | Без записи / запись обязательна |
| Лимит мест | | Если задан — после заполнения запись закрывается, работает лист ожидания |
| Срок записи | | По умолчанию до начала мероприятия |
| Награда в степах | ✔ | Можно 0 |
| Способы отметки посещения | ✔ | Любая комбинация: QR-код, кодовое слово, отметка по списку |
| Окно чек-ина | ✔ | По умолчанию от начала до окончания плюс 30 минут |
| Статус | ✔ | Черновик / опубликовано / отменено / завершено |

### 5.2. Функции студента
- Календарь в двух видах: **месяц** (сетка) и **список** (ближайшие).
- Фильтры: категория, «только мои», «только с наградой».
- Студент видит только мероприятия своей аудитории.
- Кнопки «Записаться» и «Отменить запись». Отмена возможна до начала мероприятия.
- Лист ожидания: когда освобождается место, первый в очереди записывается автоматически и получает уведомление.
- Добавление мероприятия в личный календарь телефона (файл .ics).
- Отметка посещения (п. 5.4).

### 5.3. Функции администратора
- Создание, редактирование, копирование мероприятия (для повторяющихся событий).
- Повторяющиеся мероприятия: еженедельно, до даты.
- Список записавшихся: ФИО, группа, статус, время чек-ина. Выгрузка в Excel.
- Отмена мероприятия. Все записавшиеся получают уведомление.
- Если мероприятие перенесено, записавшиеся получают уведомление.

### 5.4. Подтверждение посещения
Если для мероприятия обязательна запись, отметить посещение могут только записавшиеся. Если записи нет, при чек-ине студент записывается автоматически.

**1. QR-код.**
- Администратор открывает на ноутбуке или проекторе экран «Чек-ин» с QR-кодом.
- **QR-код меняется каждые 30 секунд** (подписанный токен со сроком действия), чтобы фото кода нельзя было переслать отсутствующим.
- Студент сканирует код камерой телефона, открывается платформа (при необходимости — вход), посещение засчитывается.
- На экране администратора в реальном времени растёт счётчик отметившихся.

**2. Кодовое слово.**
- Администратор задаёт или генерирует код (например, 6 символов) и объявляет его на мероприятии.
- Студент вводит код на странице мероприятия. Код принимается только в окне чек-ина.
- Защита от подбора: не более 5 неверных попыток за 10 минут, потом временная блокировка.

**3. Отметка по списку.**
- Администратор отмечает студентов галочками в списке записавшихся. Есть поиск по ФИО и кнопка «Отметить всех».
- Можно добавить студента, который не записывался (поиск по всем).
- Отметку можно снять до начисления, то есть до завершения мероприятия. После завершения снятие отметки делает сторно.

Награда начисляется сразу при отметке, один раз на студента. В каждом случае фиксируются способ отметки и время.

### 5.5. Критерии приёмки
- 300 студентов отмечаются по QR-коду в течение 2 минут без ошибок и задержек больше 2 секунд.
- QR-код, сфотографированный и открытый через 60 секунд, отклоняется.
- Повторный чек-ин не даёт повторного начисления.

## 6. Модуль «Задания»

### 6.1. Карточка задания
| Поле | Комментарий |
|---|---|
| Название, описание, обложка | |
| Тип | Ручная проверка / автопроверка |
| Аудитория | Все / курсы / группы / специальности |
| Период | Дата начала публикации и дедлайн |
| Награда | Максимум степов |
| Лимит выполнений | Сколько студентов могут получить награду (например, «первые 50»). Опционально |
| Статус | Черновик / опубликовано / архив |

### 6.2. Задания с ручной проверкой
- Форматы ответа — администратор выбирает разрешённые: текст, ссылка, файлы или фото (до 5 файлов, до 10 МБ каждый; jpg, png, heic, pdf, docx, pptx, zip).
- Статусы ответа: *Отправлено → Принято / Отклонено / На доработке*.
- При отклонении или возврате на доработку обязателен комментарий. При статусе «На доработке» студент может отправить ответ повторно.
- **Очередь проверки** для администратора: все ответы на проверку, фильтр по заданию и группе, просмотр вложений без скачивания, быстрые кнопки «Принять» и «Отклонить», переход к следующему ответу.
- Массовое принятие отмеченных ответов.
- При принятии степы начисляются, а студент получает уведомление.

### 6.3. Задания с автопроверкой (викторины, квесты)
- Задание состоит из одного или нескольких вопросов. Типы вопросов:
  - текстовый ответ (сравнение без учёта регистра, пробелов и буквы «ё»; допускается несколько правильных вариантов);
  - выбор одного варианта;
  - выбор нескольких вариантов.
- Настройки:
  - число попыток (по умолчанию 3);
  - проходной порог (например, 80% правильных), либо начисление пропорционально числу правильных ответов;
  - показывать ли правильные ответы после завершения.
- **Квест** — цепочка вопросов, где следующий открывается только после правильного ответа на предыдущий. Например, коды спрятаны на территории колледжа.
- Правильные ответы никогда не передаются в браузер до завершения задания.

### 6.4. Критерии приёмки
- Студент не может получить награду за одно задание дважды.
- После дедлайна отправка ответа невозможна, а очередь проверки остаётся доступна.
- Правильные ответы нельзя найти в коде страницы или в сетевых запросах.

## 7. Модуль «Опросы и голосования»

### 7.1. Опрос
- Конструктор: заголовок, описание, вопросы с сортировкой перетаскиванием.
- Типы вопросов: один вариант, несколько вариантов, шкала 1–5 или 1–10, короткий текст, длинный текст, выбор из списка.
- Признак «обязательный вопрос».
- Аудитория: все, курсы, группы, специальности.
- Период проведения — открытие и закрытие.
- Награда за прохождение.
- Один студент отвечает один раз. Изменить ответы после отправки нельзя.
- Опросы **не анонимные**: администратор видит ответы каждого студента.

**Результаты:**
- сводка по каждому вопросу: распределение ответов (диаграммы), средняя оценка по шкалам, список текстовых ответов;
- фильтр сводки по группе и курсу;
- процент прохождения от целевой аудитории, в том числе по группам;
- **выгрузка в Excel**: лист «Сводка» и лист «Ответы» (строка — студент: ФИО, группа, ответы по столбцам).

### 7.2. Голосование
Отдельный тип опроса — выборы в совет обучающихся, выбор мероприятия, конкурс работ.
- Один вопрос и варианты (кандидаты или работы) с фото и описанием.
- Режим: один голос или до N голосов.
- **Итоги публичные.** Администратор настраивает, когда их видно: сразу после голосования или только после закрытия.
- Студенты видят только итоговые цифры, кто как голосовал — не видят. Администратор видит поимённый список — это нужно для проверки. Если требуется тайное голосование (выборы), это настраивается: тогда поимённые голоса не видны никому, а хранится только факт участия.
- Переголосовать нельзя.
- После закрытия публикуется страница итогов.

### 7.3. Критерии приёмки
- Студент не видит опросы чужой аудитории и не может ответить, перейдя по прямой ссылке.
- Выгрузка в Excel открывается без ошибок, ФИО и группы соответствуют ответам.
- При тайном голосовании в базе данных нет связи «студент — вариант».

## 8. Модуль «Магазин мерча»

### 8.1. Товар
| Поле | Комментарий |
|---|---|
| Название, описание, фото (до 5) | |
| Цена в степах | |
| Варианты | Например, размер S/M/L/XL — у каждого свой остаток |
| Остаток | Количество на складе |
| Лимит на студента | Например, не более 1 штуки за всё время или за семестр |
| Аудитория | Опционально: только определённые курсы |
| Статус | Черновик / в продаже / снят с продажи |

### 8.2. Покупка
1. Студент выбирает товар и вариант и нажимает «Купить». Система показывает подтверждение: цену и баланс после покупки.
2. В одной транзакции проверяются баланс, остаток и лимит. Затем степы списываются, остаток уменьшается, создаётся заказ. Одновременные покупки последнего экземпляра обрабатываются корректно.
3. Заказу присваиваются номер и **код получения** (6 символов и QR-код).
4. Статусы заказа: *Оформлен → Готов к выдаче → Выдан*, а также *Отменён*.
5. Студент приходит в пункт выдачи и показывает код. Администратор находит заказ по коду или сканирует QR и нажимает «Выдать».
6. Отмена:
   - студент может отменить заказ до статуса «Готов к выдаче»;
   - администратор может отменить заказ в любом статусе до выдачи;
   - при отмене степы возвращаются, остаток восстанавливается.
7. Если заказ не забран за N дней (настройка, по умолчанию 30), его можно автоматически отменить с возвратом степов. Студент получает уведомление.

### 8.3. Функции администратора
- Каталог: добавление товаров и пополнение остатков.
- Список заказов с фильтрами по статусу и товару.
- Экран «Выдача»: поле для кода, сканер QR с камеры, кнопка «Выдать».
- Уведомление «Заканчивается товар», когда остаток ниже порога.

### 8.4. Критерии приёмки
- 50 одновременных покупок последних 10 единиц товара создают ровно 10 заказов. Остаток не уходит в минус, деньги списываются только у тех, у кого покупка прошла.
- Выданный заказ невозможно отменить.

## 9. Модуль «Розыгрыши»

Розыгрыши — бесплатный способ получить приз. Степы на участие не тратятся.

### 9.1. Карточка розыгрыша
| Поле | Комментарий |
|---|---|
| Название, описание, фото приза | |
| Призы | Список призов: название и количество. Например, «Наушники ×1», «Футболка ×3» |
| Период приёма заявок | Начало и окончание |
| Дата и время розыгрыша | По умолчанию — сразу после окончания приёма заявок |
| Условия участия | Комбинация условий, все должны выполняться (см. ниже) |
| Аудитория | Все / курсы / группы / специальности |

### 9.2. Условия участия (настраиваются администратором)
1. **Посетил не менее N мероприятий за период** (от и до; опционально — только мероприятия выбранной категории).
2. **Участвовал в конкретном мероприятии, выполнил задание или прошёл опрос** — одно или несколько, выбираются из списка.
3. **Принадлежит к выбранным группам, курсам или специальностям.**

Архитектура условий должна позволять добавлять новые типы условий без переделки модуля. Например, «заработал не менее N степов» или «имеет достижение X».

### 9.3. Сценарий
1. Студент видит розыгрыш и **индикатор выполнения условий** (например, «Посещено 2 из 3 мероприятий ✔✔○»).
2. Когда все условия выполнены, становится активной кнопка **«Участвую»**. Студент нажимает её и попадает в список участников.
3. В назначенное время система **автоматически** выбирает победителей:
   - каждый участник получает не больше одного приза;
   - условия перепроверяются в момент розыгрыша;
   - используется криптографически стойкий генератор случайных чисел;
   - для прозрачности сохраняются и публикуются: число участников, время розыгрыша, хэш списка участников и зерно (seed), по которым результат можно перепроверить.
4. Победители получают уведомление. Для каждого выигрыша создаётся заказ с кодом получения, выдача идёт так же, как в магазине (п. 8.2).
5. Публикуется страница итогов: призы и победители (имя, первая буква фамилии, группа).
6. Если приз не забран за N дней, администратор может провести **перерозыгрыш** этого приза среди остальных участников.

### 9.4. Функции администратора
- Создание розыгрыша и предпросмотр: «Сейчас условиям соответствуют N студентов».
- Список участников, выгрузка в Excel.
- Ручной запуск розыгрыша раньше срока (например, вживую на мероприятии) с анимацией выбора на экране.

### 9.5. Критерии приёмки
- Студент, не выполнивший условия, не может стать участником, в том числе через прямой запрос к API.
- Розыгрыш нельзя провести повторно. Результат после проведения неизменен.

## 10. Рейтинги и достижения

### 10.1. Рейтинг студентов
- Строится по **заработанным** степам, а не по балансу. Иначе покупки наказывали бы студента.
- Периоды: текущий месяц, текущий семестр, учебный год, всё время.
- Фильтры: весь колледж, мой курс, моя группа.
- Показывается топ-50 и собственное место студента.
- Студент может скрыть себя из публичного рейтинга в настройках профиля. Место видно только ему.

### 10.2. Рейтинг групп
- Метрика — **средние заработанные степы на одного студента группы**, чтобы большие группы не имели преимущества. Дополнительно показываются сумма и процент активных студентов (хотя бы одно действие за период).
- Периоды те же, что в рейтинге студентов.

### 10.3. Достижения (бейджи)
- Достижения создаёт администратор: название, описание, иконка, награда в степах (опционально), условие.
- Типы условий:
  - посещено N мероприятий (всего или по категории);
  - выполнено N заданий;
  - пройдено N опросов;
  - заработано N степов за всё время;
  - первая покупка;
  - участие в конкретном мероприятии.
- Есть ручная выдача достижения администратором — для уникальных наград.
- Условия проверяются автоматически после каждого релевантного действия.
- Получение достижения сопровождается уведомлением и анимацией.
- Набор достижений по умолчанию: «Первый шаг» (первое мероприятие), «Завсегдатай» (10 мероприятий), «Голос колледжа» (5 опросов), «Покупатель» (первая покупка), «Марафонец» (500 степов).

## 13. Нефункциональные требования

### 13.1. Производительность
- Время ответа страниц (p95) — не более 1 секунды при 300 одновременных пользователях.
- Чек-ин — не более 2 секунд при 300 отметках за 2 минуты.
- Генерация отчёта или выгрузки по 1500 студентам — не более 10 секунд. Тяжёлые выгрузки формируются в фоне со ссылкой на скачивание.

### 13.2. Надёжность
- Доступность — 99% в учебное время (8:00–20:00, пн–сб).
- Резервное копирование базы данных ежедневно, хранение 14 дней. Копии хранятся вне основного сервера (объектное хранилище в РФ). Восстановление проверяется раз в семестр.
- Загруженные файлы тоже резервируются.

### 13.3. Безопасность
- Только HTTPS (TLS 1.2+), HSTS.
- Защита от OWASP Top-10: CSRF, XSS, SQL-инъекций, IDOR. Права проверяются на сервере для каждого объекта.
- Ограничение частоты запросов (rate limiting) на вход, ввод кодовых слов и покупки.
- Пароли хранятся только в виде хэша (Argon2 или PBKDF2).
- Загружаемые файлы проверяются по типу и размеру и отдаются с заголовком `Content-Disposition`. Исполняемые форматы запрещены.
- Журнал действий администраторов: создание, изменение, удаление объектов, начисления, выдачи, импорт. Записи неизменяемы, хранятся 1 год.
- Секреты (ключи МЭШ, VAPID, БД) хранятся в переменных окружения, а не в репозитории.

### 13.4. Персональные данные (152-ФЗ)
- Серверы и резервные копии находятся на территории РФ.
- Обрабатывается минимум данных: ФИО, группа, курс, специальность, e-mail или логин mos.ru, дата рождения (только для сопоставления, опционально). СНИЛС, паспортные данные и адреса не обрабатываются.
- Нужны «Политика обработки персональных данных» и согласие студента. Согласие подтверждается при первом входе. За студентов младше 18 лет согласие даёт законный представитель — **порядок уточнить с юристом колледжа** (возможно, согласие уже собрано колледжем при зачислении).
- Колледж как оператор подаёт уведомление в Роскомнадзор, если это ещё не сделано.
- Данные выбывших студентов удаляются или обезличиваются через N месяцев после выбытия (срок задаётся). Агрегированная статистика сохраняется.

### 13.5. Удобство использования
- Mobile-first, корректная работа на экранах от 360 px.
- Браузеры: две последние версии Chrome, Яндекс Браузера, Safari (iOS 15+), Firefox, Edge.
- Интерфейс полностью на русском языке.
- Базовая доступность: контраст текста AA, работа с клавиатуры, подписи к полям.
- Основные действия студента (записаться, отметиться, купить) — не больше 3 нажатий с главной.

```
Answer(completion?, question, значение)         — при тайном голосовании без ссылки на user

Product(…, цена, лимит_на_студента, статус) / ProductVariant(product, название, остаток)
Order(user, variant | prize, цена, статус, код_получения, источник[покупка/розыгрыш], выдал, выдано)

Draw(…, период_заявок, время_розыгрыша, статус, seed, хэш_участников)
DrawCondition(draw, тип, параметры JSON)
DrawPrize(draw, название, количество)
DrawEntry(draw, user, время) / DrawWinner(draw, prize, user, order)

Achievement(…, тип_условия, параметры JSON, награда) / UserAchievement(user, achievement, время)
Notification(user, тип, текст, ссылка, прочитано) / PushSubscription(user, endpoint, ключи)
AuditLog(actor, действие, объект, изменения JSON, ip, время)
Settings(название_валюты, формы_склонения, лимиты, …)
```

### 14.4. Ключевые технические решения
- Все операции со степами, остатками и розыгрышами выполняются в транзакциях БД с блокировкой строк (`SELECT … FOR UPDATE`).
- Ротация QR-кода: в QR зашит токен `HMAC(event_id, временной_интервал)`. Принимается текущий и предыдущий интервал.
- Видимость контента по аудитории проверяется одной общей функцией для всех модулей.
- Условия розыгрышей и достижений — подключаемые «проверяльщики» (стратегии) с параметрами в JSON.
